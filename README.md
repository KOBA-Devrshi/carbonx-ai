## A. What was built

This was built from scratch as a new implementation of the stack you
specified (no prior repo existed to inspect/refactor). Three parts:

1. **`backend/`** — FastAPI + SQLAlchemy + PostgreSQL-ready (SQLite by
   default for zero-setup demo). A full relational schema (15 tables) and
   eight service modules doing the actual math: emission calculation,
   Carbon DNA (SHA-256 canonical hashing), AI vs AI audit (rule engine +
   scikit-learn IsolationForest anomaly scoring), stress testing, composite
   risk scoring, buyer matching, risk-adjusted pricing, and revalidation.
   28 REST endpoints across 9 routers.
2. **`frontend/`** — Next.js 14 App Router, TypeScript, Tailwind, Recharts.
   Landing page, dashboard, marketplace, a 7-tab credit detail page (the
   demo centerpiece), buyer matching, CSV ingestion, and an admin/audit-log
   console — all calling the real backend, no mock data in the frontend.
3. **`blockchain/`** — a Solidity contract (`CarbonDNARegistry.sol`) that
   compiles cleanly against solc 0.8.26, plus a Hardhat scaffold and a
   Python adapter in the backend that honestly reports "Demo Mode — not
   connected" instead of fabricating a transaction (see section G for why
   it isn't deployed).

**Testing performed while building** (not just claimed — actually run):
seeded the database through the real audit/DNA/risk pipeline; started the
API server and exercised all 28 endpoints with `curl`, including the
integrity-lock → blocked-purchase → clear → successful-purchase sequence,
a CSV upload that correctly flagged a synthetic "suspicious" row as
`CRITICAL`/`REJECT`, and DNA generate/verify round-trips; ran `npm run
build` on the frontend to confirm a clean TypeScript compile and static
build of all 8 routes; compiled the Solidity contract and generated its ABI.

Defender/Auditor statements, findings, and pricing/matching explanations

no latency, no non-determinism during judging) rather than a limitation of
the architecture. `ai_audit.py` exposes `OPENAI_AVAILABLE` as a ready
integration point if you want to swap in real LLM narrative generation
later; the numeric scoring (which actually drives state transitions) should
stay deterministic either way.

## C. How to run it

### Backend
```bash
cd backend
python3 -m venv venv && source venv/bin/activate   # optional but recommended
pip install -r requirements.txt
cp .env.example .env        # defaults work as-is for the demo
python seed.py               # seeds 5 demo projects through the real pipeline
uvicorn main:app --reload --port 8000
```
API docs (interactive): http://localhost:8000/docs

### Frontend
```bash
cd frontend
npm install
cp .env.local.example .env.local   # NEXT_PUBLIC_API_URL=http://localhost:8000
npm run dev
```
App: http://localhost:3000

### Blockchain (optional — not required for the demo)
```bash
cd blockchain
npm install
cp .env.example .env        # POLYGON_RPC_URL + POLYGON_PRIVATE_KEY
npx hardhat compile
npx hardhat run scripts/deploy.js --network amoy
# then set CARBON_DNA_CONTRACT_ADDRESS in backend/.env to the deployed address
```

### Postgres instead of SQLite
Set `DATABASE_URL` in `backend/.env` to
`postgresql+psycopg2://user:password@localhost:5432/carbonx`, `pip install
psycopg2-binary`, then re-run `python seed.py`. No code changes needed —
`database/session.py` reads `DATABASE_URL` directly.

## Real Blockchain & Real AI Pass

This pass answers directly: **what is genuinely done vs. what needs you to
flip a switch, and exactly how to flip it.**

### Blockchain — what changed

`services/blockchain.py`'s `record_lifecycle_event()` was, until this
pass, an honest stub: it checked configuration and returned "Demo Mode" or
a hardcoded "Contract call not wired" reason. **It now actually builds the
transaction** — loads the real ABI (generated earlier by compiling
`CarbonDNARegistry.sol` with solc 0.8.26), constructs the `recordEvent(...)`
call, signs it with the configured private key, submits it, and waits for
a receipt.

**Proof, not just claim:** this sandbox has no route to a real Polygon RPC
endpoint, so I deployed the actual compiled contract bytecode to a local
in-memory Ethereum-compatible chain (`eth-tester`) and called
`record_lifecycle_event()` through the *exact same production function* —
only the RPC endpoint and chain were swapped for a local one. The test:
deployed the contract → called the real function → read the event back
**off the chain itself** (`getEventCount`, `getEvent`,
`verifyFingerprint`) to confirm the write actually happened, not just that
the call didn't throw. All assertions passed, including a cryptographic
match on the stored fingerprint. Deploying to Polygon Amoy instead of the
local chain is now purely a configuration change — no more code to write.

**Exact steps to make it live on Polygon Amoy:**

1. **Get a wallet + private key.** Create a fresh MetaMask wallet — use a
   burner, never a wallet holding real funds, since the key goes in a
   `.env` file. Export its private key (MetaMask → Account details →
   Export Private Key).
2. **Get testnet funds.** Visit
   [faucet.polygon.technology](https://faucet.polygon.technology), select
   "Amoy," paste your wallet address, request test POL. This is free.
3. **Get an RPC URL.** Either use the public one —
   `https://rpc-amoy.polygon.technology` — or sign up free at
   [Alchemy](https://www.alchemy.com) or [Infura](https://www.infura.io)
   and create an Amoy app for a more reliable endpoint.
4. **Deploy:**
   ```bash
   cd blockchain
   npm install
   cp .env.example .env
   # edit .env: POLYGON_RPC_URL=<your RPC url>, POLYGON_PRIVATE_KEY=<your key, no 0x prefix issues either way>
   npx hardhat compile
   npx hardhat run scripts/deploy.js --network amoy
   ```
   This prints the deployed contract address.
5. **Wire it to the backend:**
   ```bash
   cd ../backend
   # edit .env: add the same POLYGON_RPC_URL and POLYGON_PRIVATE_KEY,
   # plus CARBON_DNA_CONTRACT_ADDRESS=<address from step 4>
   ```
6. **Restart the backend.** `GET /api/system/blockchain/status` should now
   show `"connected": true, "status": "Live Testnet"`. Generate a Carbon
   DNA fingerprint or flag an integrity review on any credit — that call
   now anchors on-chain for real, and `record_lifecycle_event()` returns a
   genuine `tx_hash` and `block_number` you can look up on
   [amoy.polygonscan.com](https://amoy.polygonscan.com).

No further code changes are needed for this — the wiring is done and
tested; only credentials are missing, on purpose (never committed).

### AI vs AI Audit — what changed

The deterministic engine (rule-based findings + IsolationForest anomaly
score) was always real and remains the **sole source of truth** for every
number: `confidence_score`, `risk_level`, `recommendation`,
`anomaly_score`, and the `findings` list. What was missing was the LLM
half of the brief's own hybrid-AI requirement — the Defender/Auditor
*narrative text* was always template-generated, never LLM-generated, even
when a key was present. `services/ai_audit.py` now has a real
`llm_narrate()` function wired into `run_audit()` that calls OpenAI
(`gpt-4o-mini` by default, configurable via `OPENAI_MODEL`) to re-word the
Defender/Auditor statements — grounded in the already-computed facts,
never allowed to invent new findings or change the outcome.

**Proof, not just claim:** this sandbox has no route to `api.openai.com`,
so I fully mocked the `openai` client's response shape and ran four
scenarios end-to-end:
1. No API key → falls back to deterministic text (`narrative_source:
   "deterministic"`).
2. Key + working mock → LLM text used (`narrative_source: "llm"`), and I
   asserted the prompt sent to the "LLM" actually contained the real
   computed defender score and finding text — proving it's grounded, not
   free-floating.
3. Key + a mock that raises (simulating a network failure) → falls back
   to deterministic text, no exception escapes.
4. Ran the **full `run_audit()`** twice — once with the LLM mocked on,
   once off — and asserted `defender_score`, `findings`, `anomaly_score`,
   `confidence_score`, `risk_level`, and `recommendation` were **byte-for-
   byte identical** between the two runs. Only the narrative text and
   `narrative_source` differed. This is the concrete proof that the LLM
   narrates but never decides.

**Exact steps to turn it on:**
```bash
cd backend
# edit .env: OPENAI_API_KEY=sk-...  (optionally OPENAI_MODEL=gpt-4o-mini or another chat model)
```
Restart the backend. `GET /api/system/ai-status` now reports
`"narrative_llm_configured": true`. Run any audit — the Defender/Auditor
text in the response will read more naturally; `narrative_source` in the
response tells you which path generated it, every time, so this is never
silently ambiguous. If the OpenAI call ever fails mid-demo (rate limit,
network blip), the audit still returns a complete, correct result — it
just falls back to the deterministic wording for that one call.

## Agent Pass — Voice + Text CarbonX Intelligence Agent

**No backend changes this pass** — the agent is a frontend layer that
calls the exact same REST endpoints the rest of the UI uses
(`lib/api.ts`), so everything it does is a real, auditable API call, not a
simulation of one.

### What was built

- `lib/agent/nlu.ts` — a **deterministic** keyword/regex intent parser
  (navigate, investigate, audit, verify DNA, stress test, revalidate,
  lock/clear, pricing, risk summary, blockchain, matching, why, demo,
  confirm/cancel, help). No LLM in this loop by design — see rationale
  below. Smoke-tested against 22 example commands drawn directly from the
  brief's own command list (`npx tsx` run during this build); one real bug
  was caught and fixed: "investigate this credit" was literally searching
  for a project named "this" instead of falling back to the credit already
  in context — now it correctly resolves the pronoun to `null` and falls
  back to whatever credit is currently selected.
- `context/AgentContext.tsx` — the engine. Holds conversation state
  (selected credit — auto-tracked from the URL when you open a credit
  normally, *and* settable by voice/text — last audit findings, pending
  confirmations), executes intents against the real backend via `api.ts`,
  drives the orb's state machine, and wraps the browser's
  `SpeechRecognition` / `SpeechSynthesis` APIs with feature detection,
  permission-denied handling, and interruption (pressing the mic while the
  agent is speaking stops speech and starts listening, per the brief).
- `components/agent/CarbonAgentWidget.tsx` — the floating widget (bottom
  right, every page): mode switcher (🎙 Voice / 💬 Chat), an animated orb
  (idle/listening/thinking/executing/speaking/error — CSS + Framer Motion,
  not WebGL, to keep it light on top of the 3D core already on the
  landing page), a waveform during listening, inline tool-execution
  checklists per agent message (e.g. "✓ Retrieved credit ✓ Ran AI audit ●
  Checking blockchain…"), voice settings (voice picker from
  `speechSynthesis.getVoices()`, speed, auto-speak, mic availability), and
  a text input supporting Enter-to-send / Shift+Enter-for-newline.
- `lib/agent/speech.d.ts` — ambient TypeScript types for the
  (still-unstandardized) `SpeechRecognition` API, since it isn't in the
  default DOM lib.

### Conversation memory, concretely

The agent tracks `selectedCreditId` two ways: automatically, by watching
the URL (`usePathname`) whenever you open `/credits/{id}` through the
normal UI — so if you browse to a credit and then ask "is this risky?" by
voice, it already knows which one; and explicitly, whenever a voice/text
command names or discovers a credit ("investigate Reforestation
Maharashtra", "show me the riskiest credit"). Follow-up commands
("audit it", "lock this", "why?") reuse that state without re-asking for
an ID, exactly as the brief's example conversation describes.

### Confirmation gate on Lock / Clear

Both `LOCK` and `CLEAR_LOCK` intents never call the backend directly —
they set a pending-confirmation state and ask first ("Should I place this
credit under Integrity Review? Say 'confirm' to proceed"), matching the
demo script's own "ask for confirmation, then lock" beat. Saying anything
else clears the pending action rather than silently executing it.

### Voice Demo Mode

"Give me the demo" / "give me a tour" runs a scripted sequence: navigate
to marketplace → open the Reforestation Maharashtra credit (found by name
match, not hardcoded ID, so it still works if you re-seed) → generate +
verify DNA → run the AI audit → run a stress-test scenario → check the
resulting risk level and, if it's HIGH/CRITICAL, ask to lock it. Every
step is a real API call; the only "scripting" is the order and the spoken
narration between them.

### Failure handling, tested

- **No SpeechRecognition support** (or denied permission): mic button
  disables, a plain-language banner appears, text chat keeps working —
  verified by reading the feature-detection branch logic; this sandbox
  can't launch a real browser to click "deny," so this is confirmed by
  code inspection, not a live permission-denial click-test (see
  Limitations).
- **No SpeechSynthesis support**: `synthSupported` gates the Voice
  Output toggle; `speak()` resolves immediately without throwing if
  unsupported, so responses still render as text.
- **Backend unreachable**: every tool call is wrapped in `runWithSteps`'s
  try/catch, which replaces the pending message with "CarbonX
  Intelligence Service Unavailable — …" rather than hanging or crashing
  the widget.
- **No LLM / OPENAI_API_KEY**: not applicable to this feature — the agent
  never depended on one. See rationale below.

### Why no LLM in the understanding loop

The brief explicitly requires "If LLM fails: use deterministic CarbonX
command handling" as a fallback. Given an offline demo with no guaranteed
internet, I made the fallback the *only* path rather than building a
primary LLM-based NLU with a deterministic backup I couldn't fully
rehearse-test in this session. This is consistent with the earlier scoping
decision for the AI-audit feature (deterministic rules + IsolationForest
as the source of truth, LLM narrative never wired) — same reasoning
applies here. Swapping in a real LLM later is additive: point it at
`parseIntent`'s output shape (`{type, params}`) and keep it advisory,
never load-bearing for financial/integrity state, per the brief's own
Part 25 rule.

### Limitations — stated plainly

- **No live browser test of microphone/speech flows.** This sandbox has
  no display or real browser to click "allow microphone," speak into a
  fake mic, or hear synthesized audio — all voice-path correctness is
  from code inspection and the deterministic NLU test, not an end-to-end
  click-and-listen test. Test this for real on the presentation laptop
  before tomorrow, specifically: mic permission prompt, actual speech
  recognition accuracy, and that `speechSynthesis.getVoices()` returns
  voices in the browser you'll present with (Chrome is the safest choice
  — Safari's `SpeechRecognition` support is inconsistent).
- **The 3D orb described in the brief (rotating rings, particles, energy
  waves synced to speech) was not built.** I built a CSS/Framer-Motion orb
  with real state-driven pulsing instead — reusing WebGL for a second
  component on top of the landing page's Carbon Intelligence Core risked
  hurting the "smooth on a laptop" requirement for comparatively little
  demo value versus the orb's actual job (showing agent state clearly).
  Stated plainly: **UI implemented with a lighter-weight orb; the
  described 3D orb with particle system was not built.**
- **No attachment upload (📎) in the input bar** — the brief lists it as
  optional ("📎 optional attachment"); not implemented, since nothing in
  the agent's toolset consumes an attachment yet (CSV upload already has
  its own dedicated page).
- **Push-to-talk exists in the engine** (`startPressToTalk`/
  `endPressToTalk`) but isn't wired to a press-and-hold gesture on the mic
  button in the widget — only click-to-toggle is wired in the UI. The
  functions are there; connecting `onMouseDown`/`onMouseUp` is a small
  follow-up if you want press-and-hold specifically.

**unchanged in logic** and was re-verified end-to-end after every edit in
this pass (21/21 endpoint checks passed in the final regression run,
including the integrity-lock → HTTP 423 → clear → purchase-succeeds
sequence).

**Interconnection, verified live, not just asserted:** flagging a credit
for integrity review immediately blocks `POST /marketplace/{id}/purchase`
with HTTP 423 — enforced server-side, the frontend button being disabled is
a courtesy, not the actual control. Running the AI audit on a
low-evidence-quality credit lowers `audit_confidence`, which the risk
engine folds into `composite_risk` on every subsequent call, which the
pricing engine reads live to widen the fair-value discount, and which the
matching engine reads live to rank that credit lower for
confidence-sensitive buyers — all by re-querying current DB state on each
request, not by copying values forward. No caching layer sits between them
that could go stale.

## G. Known limitations — stated plainly

- **Blockchain is not deployed.** The contract compiles cleanly (verified
  with solc 0.8.26 during this build) but this sandbox has no route to a
  Polygon RPC endpoint or the Solidity binary registry a full Hardhat
  install needs, so it was never pushed to Amoy testnet. The backend
  adapter is honest about this — it reports `"status": "Demo Mode"` and
  `reason: "Not configured: ..."` rather than inventing a transaction hash.
  Deploying is three commands (section C) once you have normal internet
  access and a funded testnet wallet.
- **No authentication.** Anyone who can reach the API can call any
  endpoint, including admin-only actions like clearing an integrity
  review. Fine for a local demo, not for anything beyond that.
- **AI reasoning is deterministic, not an LLM**, by design (see section B)
  — genuinely swappable behind `ai_audit.py`, but not wired to
  `OPENAI_API_KEY` in this build even when the key is present.
- **XGBoost was swapped for scikit-learn's `IsolationForest`** — same
  category of ML anomaly model, lighter dependency, faster to verify in
  this environment. Swapping in XGBoost is a service-layer change only.
- **CSV ingestion is intentionally minimal** — it validates the documented
  schema and flags negative values / reported-exceeds-baseline rows, but
  it isn't a general-purpose ETL pipeline.
- **The frontend build's font-optimization step is skipped in this
  sandbox** (no route to `fonts.googleapis.com`) — the app still builds
  and runs correctly with system font fallbacks; on a machine with normal
  internet access, the Google Fonts `<link>` tags in `app/layout.tsx` will
  load normally.
- **Demo data is synthetic**, clearly marked `demo_data: true` in the
  `Project` table, and the frontend's disclaimer banner says so. Nothing
  here is a certified carbon credit.
- **CORS is wide open to `localhost:3000` only by default** — update
  `CORS_ORIGINS` before deploying anywhere else.
